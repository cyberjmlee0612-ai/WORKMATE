# WORKMATE 1차 구현 PRD

기준: [Notion 개발 진행 기록](https://app.notion.com/p/41bc606cb89c812c8436fdd052d6a984), 2026-11-24 확인. 이 문서는 1차 구현 범위를 정한다. 원문에서 확정되지 않은 정책은 아래 **구현 전 결정 사항**으로 분리한다.

## 1. 프로젝트 개요 및 핵심 목표

WORKMATE는 프로젝트 업무와 프로젝트에 속하지 않은 개인 업무를 관리하는 서비스다. 장기적으로 자연어 업무 입력과 AI 계획 제안을 제공하지만, 1차 목표는 인증부터 CRUD, 상태 관리, 대시보드 집계까지 실제 데이터로 동작하는 기본 제품이다. AI가 만든 제안은 향후에도 사용자 검토·승인 전 자동 저장하지 않는다.

- 프론트엔드: Next.js App Router, React, TypeScript, Tailwind CSS.
- 백엔드: Python, FastAPI. 인증은 Supabase Auth, 영속 데이터는 Supabase PostgreSQL.
- UI와 데이터 접근 계층을 분리한다. 정적 예시 데이터와 하드코딩된 KPI를 실제 조회 및 계산으로 교체한다.
- 모든 사용자 데이터는 소유자 기준으로 격리한다. Supabase RLS를 적용하고 서버에서도 소유권을 확인한다.
- 기존 디자인 방향인 Soft Glass × Liquid Accent, 녹색 계열, 접이식 사이드바와 반응형 레이아웃을 유지한다.

## 2. 사용자 시나리오 및 MVP 우선순위

| 우선순위 | 시나리오 | 완료 기준 |
| --- | --- | --- |
| P0 | 사용자가 가입·로그인하고 본인 공간에 접근한다 | 비로그인 사용자는 보호 화면에 접근할 수 없고, 다른 사용자의 데이터가 보이지 않는다 |
| P0 | 프로젝트를 만들고 목록·상세에서 조회·수정한다 | 새로고침 후에도 데이터가 유지된다 |
| P0 | 프로젝트 업무 또는 독립된 개인 업무를 만들고 조회·수정·삭제한다 | `project_id = NULL`인 업무를 개인 업무로 구분하고, 전체 업무 화면에는 둘 다 표시한다 |
| P0 | 업무 상태·우선순위·마감일을 바꾸고 완료 체크를 한다 | 상태 및 `completed_at`이 일관되게 저장되고 화면과 KPI가 즉시 갱신된다 |
| P0 | 대시보드에서 프로젝트·업무 현황을 본다 | KPI와 프로젝트 진행률이 실제 업무 데이터에서 계산된다 |
| P0 | 프로젝트를 삭제할 때 연결 업무의 처리 방법을 고른다 | 보존할 업무만 개인 업무로 이동하거나 업무와 함께 삭제하며, 전체 작업은 원자적으로 처리된다 |
| P1 | 프로젝트를 완료·보관하고 다시 열거나 이전 상태로 복원한다 | 미완료 업무가 있어도 완료 가능하며, 완료 당시 미완료 개수를 보여주고 기존 데이터가 유지된다 |
| P1 | 불필요해진 업무를 취소 상태로 보존한다 | 삭제와 구분되고 완료 수 및 진행률 계산에서 제외된다 |

구현 순서: 인증·RLS·스키마 → 프로젝트 CRUD → 업무 CRUD 및 개인 업무 분리 → 상태 변경·집계 → 프로젝트 삭제 흐름 → 완료·보관·취소 흐름. P1의 세부 이력·보존 정책은 구현 전 결정 사항을 먼저 확정한다.

| 화면 | 주요 요소 | 동작 규칙 |
| --- | --- | --- |
| 가입·로그인 | 이메일 기반 Supabase Auth 화면, 오류·로딩 상태 | 인증 성공 후 대시보드 이동. 가입 시 간편/상세 모드 선택 요구는 확정됐으나 모드별 UI 정의 전에는 기능 차이를 임의로 만들지 않는다 |
| 대시보드 | 인사말, 새 프로젝트, KPI 4종, 프로젝트 목록, 오늘의 업무 | 전체 프로젝트·전체 업무·완료 업무·전체 진행률을 실제 데이터로 표시. 업무 완료 체크 시 서버 저장 후 관련 수치 재조회/갱신. 오늘의 업무 선정 기준은 구현 전 결정 |
| 프로젝트 목록 | 활성 프로젝트 카드, 상태, 진행률, 생성 버튼, 완료 프로젝트 구역 | `completed`는 진행 목록에서 분리. `archived`의 표시 위치는 구현 전 결정. 업무가 0개면 진행률 0%를 임시 기준으로 사용 |
| 프로젝트 생성·수정 | 이름, 설명, 상태, 시작일, 마감일 | 이름의 공백 입력 금지. 두 날짜가 모두 있으면 시작일 ≤ 마감일. 저장 성공 후 목록·상세에 반영 |
| 프로젝트 상세 | 프로젝트 정보, 소속 업무 목록, 진행률, 수정·완료·복원·삭제 | 소속 업무만 조회. 미완료 업무가 있어도 완료 가능하며 완료 전 개수를 확인시킨다. 복원 시 같은 프로젝트·업무 ID 유지 |
| 업무 전체(Task Management) | 프로젝트 업무와 개인 업무의 통합 목록, 상태·우선순위·마감일, 생성·편집·삭제 | 필터에서 개인 업무를 구분. 상태는 `todo` → `in_progress` → `review` → `completed` 중 임의 선택 가능; 전이 제한은 정해지지 않았으므로 추가하지 않는다 |
| 개인 업무(Personal Tasks) | `project_id IS NULL`인 업무 목록과 생성 | 프로젝트 없이 생성 가능. 프로젝트 업무를 개인 업무로 바꿀 때 소유권을 검증한다 |
| 업무 폼 | 제목, 설명, 프로젝트 선택(없음 가능), 상태, 우선순위, 마감일, 예상 소요 시간 | 제목 공백 금지, 예상 시간은 비어 있거나 양의 정수. 완료로 바꾸면 `completed_at` 기록, 완료에서 벗어나면 초기화 |
| 프로젝트 삭제 대화상자 | A 개인 업무로 이동, B 삭제 취소, C 업무도 함께 삭제 | 연결 업무 0개: 프로젝트 삭제 확인만. A: 업무 목록 슬라이드 열기/접기, 초기 전체 선택, 모두 선택/해제, 개별 선택. 0개 선택이면 진행 불가. 최종 확인에서 보존/삭제 업무를 분리 표시. C: 삭제 업무 목록·개수와 최종 확인. B: 데이터 변경 없음 |

공통: 저장·삭제 버튼은 처리 중 중복 실행을 막고, 실패하면 입력값을 유지하며 오류를 표시한다. 데스크톱은 사이드바와 KPI 4열, 태블릿은 축소 사이드바와 KPI 2열, 모바일은 하단 메뉴와 KPI 1열을 기준으로 한다.

## 4. 데이터 구조 및 API/연동 요구사항

### 데이터 모델

`auth.users.id`를 사용자 식별자로 사용한다. 별도 Users 테이블은 1차 필수 사항이 아니다. 테이블명은 예시이며 SQL 작성 시 확정한다.

| 엔터티 | 필드: 타입 | 규칙 |
| --- | --- | --- |
| Projects | `id: UUID`, `user_id: UUID`, `name: TEXT`, `description: TEXT?`, `status: TEXT`, `start_date: DATE?`, `due_date: DATE?`, `created_at: TIMESTAMPTZ`, `updated_at: TIMESTAMPTZ` | `id`, `user_id`, `name`, `status`, 시각 필수. 상태: `planning`, `in_progress`, `review`, `completed`, `archived` |
| Tasks | `id: UUID`, `user_id: UUID`, `project_id: UUID?`, `title: TEXT`, `description: TEXT?`, `status: TEXT`, `priority: TEXT`, `due_date: DATE?`, `estimated_minutes: INTEGER?`, `completed_at: TIMESTAMPTZ?`, `created_at: TIMESTAMPTZ`, `updated_at: TIMESTAMPTZ` | `project_id = NULL`이면 개인 업무. 상태: `todo`, `in_progress`, `review`, `completed`; 취소 기능을 포함하면 `cancelled` 추가. 우선순위: `low`, `medium`, `high`, `urgent` |

P1을 구현할 때는 프로젝트 완료 시각과 완료 당시 미완료 업무 수를 보존할 구조, 완료·복원 이력, 업무 취소 시각/사유의 필요 여부를 먼저 확정한다. 진행률은 저장 필드가 아니라 조회 시 계산한다.

### 계산 규칙

- 프로젝트 진행률 = 해당 프로젝트의 `completed` 업무 수 ÷ 해당 프로젝트의 취소되지 않은 업무 수 × 100.
- 전체 업무 = 프로젝트 업무 + 개인 업무 중 취소되지 않은 업무 수. 완료 업무 = 그중 `completed` 수. 전체 진행률 = 완료 업무 ÷ 전체 업무 × 100.
- 분모가 0이면 0% 표시. 전체 프로젝트는 보관 상태를 제외한 수를 임시 기준으로 사용한다. 이 KPI 기준은 원문에서 최종 승인 전이므로 구현 전 확인한다.
- 마감일은 날짜만 저장한다. 시각 단위 카운트다운이 필요한 기능은 별도 모델 결정 후 구현한다.

### API 계약 방향

FastAPI의 JSON API를 데이터 접근 계층에서 호출한다. 구체 경로·응답 스키마는 구현 시 OpenAPI로 고정한다.

| 리소스 | 필요한 동작 |
| --- | --- |
| Auth | Supabase Auth 가입·로그인·로그아웃·세션 복원. FastAPI는 전달된 사용자 토큰을 검증 |
| Projects | 목록/상세 조회, 생성, 수정, 완료·복원·보관, 삭제 사전 조회 및 확정 실행 |
| Tasks | 전체/프로젝트별/개인 업무 조회, 생성, 수정, 상태 변경, 삭제 |
| Dashboard | 사용자 소유 데이터의 KPI와 프로젝트별 진행률 조회 |

- 생성·수정·삭제 요청의 `user_id`는 클라이언트 입력을 신뢰하지 않고 인증 주체에서 정한다.
- 프로젝트에 업무를 연결할 때 양쪽 소유자가 같은지 검증한다. RLS로 사용자별 조회·쓰기 권한을 제한한다.
- 프로젝트 삭제 A/C는 서버 측 단일 트랜잭션으로 수행한다. 자동 CASCADE에만 의존하지 않는다. 실패 시 전체 롤백한다.
- `id`/소유자, `project_id`, 상태, 마감일 조회를 고려해 인덱스를 설계한다.
- Supabase SQL 및 RLS는 원문에서 검토·승인 전 상태다. 마이그레이션을 작성하되 적용 전 스키마·정책을 검토 대상으로 제시한다.

## 5. 예외 상황 및 edge case

- 미인증·만료 세션: 보호 API는 401, 화면은 로그인 흐름으로 안내. 타인 소유 리소스는 정보 노출 없이 거절한다.
- 빈 이름·공백 제목, 음수/0 예상 시간, 잘못된 날짜 순서, 알 수 없는 상태·우선순위: 저장 전후 모두 검증하고 필드 오류를 표시한다.
- 프로젝트가 없는 업무는 정상 데이터다. 존재하지 않거나 타인 소유 프로젝트 ID로 연결할 수 없다.
- 완료 업무를 다시 다른 상태로 변경하면 `completed_at = NULL`. 취소 업무는 완료 수·진행률 분자와 분모에서 제외한다.
- 프로젝트에 업무가 0개면 삭제 선택 목록을 생략한다. A에서 업무 선택이 0개면 확인 단계로 진행할 수 없다.
- 삭제 확인 중 다른 탭에서 업무가 변경되면 서버의 최신 소속 업무를 재검증하고 변경된 목록을 다시 확인시킨다. 중복 삭제 요청은 안전하게 처리한다.
- 네트워크 또는 DB 오류 발생 시 성공으로 표시하지 않는다. 프로젝트와 업무가 부분 삭제되거나 부분 이동되지 않아야 한다.
- 목록이 비었을 때는 생성 동작을 제공한다. 느린 요청에는 로딩 상태, 실패 시 재시도 수단을 제공한다.

## 6. 1차 구현 제외 범위(Non-goals)

- LLM 연동, 자연어 입력, AI 세분화·우선순위·일정 제안, AI 검색·분석.
- 업무 집중 타이머, 마감 카운트다운, 시간 기록·장애 복구, 알림 센터. 원문에서 상세 정책이 많지만 별도 단계로 설계·구현한다.
- 캘린더, 타임라인, 일정 드래그, 계획·실제 시간 시각화, 보고서·심층 통계.
- 통합 검색, 검색 기록·추천·저장 조건, 빠른 작업.
- 협업, 댓글, 첨부 파일, 외부 클라우드 연동, 프로젝트 복사·재사용.
- 완료 프로젝트의 보존 기간 자동화, 삭제 예정 카테고리, 백업 내보내기·복원, 영구 삭제 운영 로그. 확정된 제품 방향이지만 별도 데이터·운영 설계가 필요하다.

## 구현 전 결정 사항

1. KPI의 전체 프로젝트 범위와 업무가 없는 경우 0% 규칙을 최종 승인한다.
2. 프로젝트 `completed`·`archived` 간 전이와 복원 시 이전 상태, 완료 이력·스냅샷 저장 구조를 확정한다.
3. `cancelled` 상태를 1차 P1에 포함할지, 취소 시각·사유 및 재활성화 규칙을 확정한다.
4. 가입 시 모드 선택을 1차 화면에 넣는 경우 간편/상세 모드의 실제 차이와 설정 저장 방식을 정한다.
5. 오늘의 업무 선정 기준과 기본 정렬을 정한다.
6. 삭제 확인 화면의 세부 문구, P1 보존 정책과 1차 일반 삭제의 관계를 확정한다.

미결정 사항을 Claude가 임의로 확정해 데이터베이스에 적용하지 않는다. 먼저 선택지와 영향 범위를 제시하고 결정 후 마이그레이션·API·화면에 반영한다.
